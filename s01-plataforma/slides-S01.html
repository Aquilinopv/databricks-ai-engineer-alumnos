Qué es Databricks

Una sola plataforma para datos, analítica e IA

Lo que reemplaza

  • Un data warehouse para reportes
  • Un data lake para archivos crudos
  • Un cluster aparte para machine learning
  • Otra herramienta para orquestar

Lo que aporta

  • Un solo lugar de almacenamiento
  • Un solo modelo de permisos
  • Un solo linaje, de punta a punta
  • SQL, Python, Scala y R sobre los mismos datos

La palabra que vas a escuchar todo el curso es lakehouse: la idea de que no hace falta elegir entre lago y almacén.

Compute

Nada corre sin una máquina encendida — y ahí está el costo

Elegir mal el tipo de cluster es el error más caro que se comete en Databricks. Hay tres, y sirven para cosas distintas.

Tipo 1 · SQL Warehouse

Para consultar: SQL, dashboards y Genie

Cómo se crea

  • Compute → SQL Warehouses → Create
  • Tamaño (2X-Small alcanza para el curso)
  • Serverless: arranca en segundos
  • Auto-stop: 10 minutos

Cuándo NO

  • Si necesitas librerías de Python
  • Si vas a entrenar un modelo
  • Si el trabajo no es SQL

Es el que va a atender las consultas del Genie en la sesión 3 y las del agente en la sesión 5.

Tipo 2 · All-purpose cluster

Para desarrollar: notebooks interactivos

Cómo se crea

  • Compute → Create compute
  • Eliges versión de runtime
  • Puedes instalar librerías
  • Terminate after… ← esto siempre

Cuándo NO

  • En producción: queda encendido y se paga igual
  • Para un job programado, hay algo mejor

Es el que vas a usar hoy para el notebook, y el que hay que acordarse de apagar al terminar.

Tipo 3 · Job cluster

Para producción: nace, trabaja y muere

Cómo se crea

  • No se crea a mano
  • Se define dentro del job
  • Arranca al empezar la corrida
  • Se apaga solo al terminar

Cuándo NO

  • Para desarrollar: esperarías el arranque en cada prueba

En la sesión 2 vas a agendar un pipeline, y va a correr sobre uno de éstos sin que tengas que encender nada.

⏳

Los tres, uno al lado del otro

Elegir el compute es elegir cuánto pagas

El mismo trabajo cuesta 2,1 veces más si corre sobre un cluster interactivo en lugar de un job programado.

No es una recomendación de estilo: es el precio de lista de la región donde está este workspace. Precios reales de system.billing.list_prices para AWS us-west-2, consultados el 26 de agosto de 2026. Los vas a poder verificar tú mismo en la sesión 8.

Antes del lakehouse

Había que elegir entre gobierno y flexibilidad

Data warehouse

  • Rápido y ordenado
  • Permisos y transacciones
  • Pero: solo datos tabulares
  • Y: caro de escalar
  • Un PDF no entra. Un audio tampoco.

Data lake

  • Barato, guarda cualquier cosa
  • Escala sin límite
  • Pero: sin transacciones
  • Y: sin esquema garantizado
  • Termina siendo un pantano

Las empresas terminaban montando los dos, y copiando datos de uno al otro todas las noches.

El lakehouse

El almacenamiento del lago con las garantías del almacén

Un agente necesita las dos cosas de arriba: tablas para calcular y documentos para responder. El lakehouse las pone sobre el mismo almacenamiento y el mismo gobierno.

Para lo que hacemos en este curso importa por una razón concreta: un agente de IA necesita las dos cosas — tablas confiables para calcular, y documentos sueltos para responder.

Arquitectura medallón

Los datos no se limpian de una vez: pasan por tres capas

Bronze no se corrige: se re-procesa. Si arreglás el dato malo en bronze, perdés la evidencia de qué te mandaron realmente — y con ella, la posibilidad de demostrar que el error no era tuyo.

El problema

Sin gobierno central, cada workspace es una isla

Cómo era antes

  • Permisos definidos por workspace
  • La misma tabla, cinco copias, cinco dueños
  • Nadie sabía de dónde salía un número
  • Los archivos no tenían permisos: o veías todo el bucket, o nada

Qué cambia

  • Un catálogo por encima de todos los workspaces
  • Un solo lugar donde se dan permisos
  • Linaje automático de punta a punta
  • Tablas, archivos, modelos y funciones bajo las mismas reglas

La jerarquía

Todo lo que crees vive en este árbol

metastore→catálogo→esquema→tablavistavolumenfunciónmodelo

De ahí sale el nombre de tres niveles que vas a escribir todo el curso:

SELECT * FROM neptuno.ventas.productos
--            └catálogo└esquema└tabla

Metastore

La raíz: uno por región, compartido entre workspaces

Es el registro central donde viven los metadatos de todo. No lo creas tú: lo crea quien administra la cuenta, y se asigna a los workspaces de esa región.

Un dato que se cobra en la sesión 3: los comentarios son globales al metastore. Documentar una tabla la documenta para todos los workspaces.

★

Catálogo

El primer nivel que sí creas tú

CREATE CATALOG IF NOT EXISTS neptuno_manuel
  COMMENT 'Datos del curso Databricks AI Engineer';

USE CATALOG neptuno_manuel;
SHOW SCHEMAS;

Se usa para separar por proyecto, por entorno (desarrollo / producción) o por dominio de negocio. Hoy cada uno crea el suyo para no pisarse.

★

Esquema

Adentro del catálogo, la carpeta donde viven las tablas

CREATE SCHEMA IF NOT EXISTS neptuno_manuel.bronze;
CREATE SCHEMA IF NOT EXISTS neptuno_manuel.silver;
CREATE SCHEMA IF NOT EXISTS neptuno_manuel.gold;

Fíjate que las tres capas del medallón se vuelven tres esquemas. No es obligatorio hacerlo así, pero es la convención más común y deja el linaje legible.

Tablas

Gestionadas o externas: quién es dueño de los archivos

Gestionada

  • Unity Catalog decide dónde guardar
  • Si borras la tabla, se borran los datos
  • Es el default, y lo que usamos hoy

Externa

  • Tú indicás la ubicación
  • Si borras la tabla, los archivos quedan
  • Para datos que comparte otro sistema
CREATE TABLE neptuno_manuel.bronze.productos ...          -- gestionada
CREATE TABLE ... LOCATION 's3://mi-bucket/productos'     -- externa
★

Volumes

Lo mismo que una tabla, pero para archivos

Un volumen es una carpeta gobernada: PDFs, CSVs, imágenes, modelos. Se le dan permisos igual que a una tabla, y aparece en el linaje.

CREATE VOLUME IF NOT EXISTS neptuno_manuel.bronze.landing;

-- y se usa como una ruta normal
/Volumes/neptuno_manuel/bronze/landing/productos.csv

Acá caen hoy los CSV de Neptuno — y en la sesión 4, los documentos que va a leer el sistema de RAG.

Permisos

Se otorgan sobre cualquier nivel del árbol

GRANT USE CATALOG ON CATALOG neptuno_manuel TO `analistas`;
GRANT USE SCHEMA  ON SCHEMA  neptuno_manuel.gold TO `analistas`;
GRANT SELECT      ON TABLE   neptuno_manuel.gold.ventas TO `analistas`;

-- o de una vez, para todo lo que haya y lo que venga
GRANT SELECT ON SCHEMA neptuno_manuel.gold TO `analistas`;

Para leer una tabla hacen falta los tres: entrar al catálogo, entrar al esquema y leer la tabla. Es el error de permisos más frecuente.

Linaje

Se registra solo, y en la sesión 7 se vuelve el centro

Cada vez que una consulta lee una tabla y escribe otra, Unity Catalog anota la relación. Sin configurar nada, terminas con el mapa de qué alimenta a qué — hasta el nivel de columna.

Hoy tu linaje está casi vacío. Al final del curso vas a poder trazar una respuesta del agente hasta el CSV del que salió.

Tres formatos

Por qué no alcanza con guardar un CSV

CSVParquetDelta
Tipos de datoNoSíSí
Lee solo las columnas que pidesNoSíSí
TransaccionesNoNoSí
Historial de versionesNoNoSí
detalles_pedidos en CSV41,8 KB
la misma tabla en Delta12,5 KB
diferencia 3,4×

Medido sobre los datos de este curso. Delta es Parquet más un registro de transacciones: la compresión viene de Parquet; el historial, del registro.
⚠️ Con 2 155 filas el Delta no es más rápido que el CSV — la ventaja en velocidad aparece con volumen. Lo que sí se nota ya: la segunda consulta baja de 3,37 s a 1,47 s por caché.

Anatomía

Una tabla Delta es una carpeta con archivos y un diario

productos/
  part-00000-....snappy.parquet      -- los datos, en Parquet
  part-00001-....snappy.parquet
  _delta_log/
    00000000000000000000.json        -- se creó la tabla, se agregaron 2 archivos
    00000000000000000001.json        -- se borraron 12 filas
    00000000000000000002.json        -- se restauró a la versión 0

Ese _delta_log es todo el secreto. Cada operación agrega una entrada nueva; nunca se reescribe la anterior. De ahí salen las transacciones y el historial.

ACID

Qué significa cada garantía cuando el almacén es un bucket

Atomicidad

La escritura entra entera o no entra. Nadie ve media carga.

Consistencia

El esquema se respeta: no entra una columna de texto donde va un número.

Aislamiento

Alguien puede leer mientras tú escribes, y ve la versión anterior completa.

Durabilidad

Confirmado es confirmado, aunque se caiga el cluster.

Crear una tabla

Casi siempre, a partir de una consulta

CREATE TABLE neptuno_manuel.bronze.productos
AS SELECT * FROM ...;

-- y para leer archivos de un volumen:
CREATE TABLE neptuno_manuel.bronze.productos AS
SELECT * FROM read_files(
  '/Volumes/neptuno_manuel/bronze/landing/productos.csv',
  format => 'csv', header => true );

En bronze conviene agregar de dónde vino cada fila y cuándo entró. Esas dos columnas son las que permiten responder «¿de dónde salió este número?».

Viaje en el tiempo

Consultar el pasado, o volver a él

-- leer como estaba antes
SELECT * FROM neptuno_manuel.bronze.productos VERSION AS OF 0;
SELECT * FROM neptuno_manuel.bronze.productos TIMESTAMP AS OF '2026-08-26';

-- o directamente volver
RESTORE TABLE neptuno_manuel.bronze.productos TO VERSION AS OF 0;

Sirve para recuperar un borrado, pero también para auditar: puedes reproducir exactamente el dato que vio un reporte la semana pasada.

Mantenimiento

Dos comandos que conviene entender antes de correr

OPTIMIZE neptuno_manuel.bronze.pedidos;                -- junta archivos chicos
OPTIMIZE neptuno_manuel.bronze.pedidos ZORDER BY (IdCliente);

VACUUM neptuno_manuel.bronze.pedidos RETAIN 168 HOURS;  -- borra archivos viejos

Ojo con VACUUM: borra los archivos que ya no usa ninguna versión reciente. Después de correrlo, el viaje en el tiempo más allá del período retenido deja de funcionar.

Lo que encontramos al cargar los datos

Las ventas de Neptuno están infladas, y el error es demasiado chico para que alguien lo note

Sumando precio × cantidad1.354.458,59
Restando el descuento1.265.793,04

6,55%

Cada línea de pedido tiene un Descuento que nadie restó. Un error del 6% no dispara ninguna alarma: es demasiado chico para verse a simple vista y demasiado grande para un cierre contable. Por eso llega a producción. En la sesión 2 lo eliminamos de raíz, en un solo lugar.

Y todo esto, ¿para qué?

Porque en tres sesiones le vamos a dar estos datos a una IA

Ya tenemos dónde guardar, cómo gobernar y cómo confiar. Antes de cerrar, vale la pena ver qué pasa cuando una IA lee datos que no tienen nada de esto.

Lo que sigue es una consulta real contra este mismo dataset, hecha con lenguaje natural sobre las tablas crudas, sin documentar.

La misma pregunta, tres veces seguidas

«¿Cuál es el margen de la categoría Bebidas?»

No difieren en el decimal: ni siquiera coinciden en el signo. Dos dicen que Bebidas pierde dinero; una, que gana un cuarto de millón.

Mismos datos · mismo modelo · misma pregunta

Por qué pasó

Neptuno no tiene tabla de costos: el margen no existe

Cuando el esquema contiene la respuesta, el modelo llega siempre al mismo SQL. Cuando no la contiene, improvisa — y cada improvisación es distinta.

Si preguntás tres veces y te dan tres números, esa pregunta no tiene respuesta en tus datos.

Contraprueba: «¿cuántos pedidos hubo en 1997?» da idéntico las tres veces. El modelo no es inestable; lo inestable es pedirle lo que no puede saber.
