Pregunta 1 · managed tables

“Managed” no significa “sin mantenimiento”

Managed responde

  • ¿Quién administra la ubicación física?
  • ¿Quién elimina los archivos al hacer DROP TABLE?
  • ¿Quién gobierna permisos y metadatos?

Mantenimiento responde

  • ¿Hay demasiados archivos pequeños?
  • ¿Quedan archivos antiguos sin uso?
  • ¿El optimizador tiene estadísticas recientes?

Una tabla managed sí puede necesitar OPTIMIZE, VACUUM y ANALYZE.

Cada comando hace un trabajo

Compactar no es borrar, y borrar no es ordenar

OPTIMIZE

Compacta

Reescribe archivos para mejorar tamaño y distribución.

VACUUM

Limpia

Elimina archivos que versiones recientes ya no referencian.

ANALYZE

Mide

Recopila estadísticas para que el optimizador planifique mejor.

VACUUM puede limitar el time travel: una versión histórica deja de ser recuperable si sus archivos fueron eliminados.

La práctica actual

Predictive Optimization automatiza el mantenimiento

Unity Catalog→Managed table→OPTIMIZEVACUUMANALYZE

Si está habilitado, Databricks decide cuándo ejecutar cada operación usando serverless compute. No dupliques ese trabajo con jobs programados.

Predictive Optimization solo cubre tablas managed de Unity Catalog; no mantiene tablas externas.

Fuente: Databricks · Predictive Optimization

ZORDER y el camino moderno

Para tablas nuevas, Databricks recomienda Liquid Clustering

Enfoque tradicional

OPTIMIZE neptuno_manuel.bronze.pedidos
ZORDER BY (IdCliente);

ZORDER sigue disponible en tablas Delta sin liquid clustering.

Enfoque recomendado

ALTER TABLE neptuno_manuel.bronze.pedidos
CLUSTER BY (IdCliente);

OPTIMIZE neptuno_manuel.bronze.pedidos;

Liquid Clustering y ZORDER no se combinan.

Fuente: Databricks · Liquid Clustering

Metastore→Catálogo→Esquema→Volume→carpetas y archivos

Antes de conectar GitHub

“Only select repositories” solo muestra repos que puedes administrar

¿Por qué está vacío?

El repositorio del curso pertenece a manuelarguelles. Un alumno puede leerlo porque es público, pero no puede instalar una GitHub App sobre un repositorio ajeno.

¿Necesito hacer fork?

  • No, si solo vas a clonar, ejecutar y hacer Pull.
  • Sí, si quieres hacer commits y Push desde Databricks.

Para seguir el curso: clona el repo público y omite OAuth.

Fuentes: Databricks · Git credentials · GitHub · Installing a GitHub App

Si quieres escribir · fork + OAuth

Primero crea una copia que pertenezca a tu cuenta

1

En GitHub, abre el repositorio del curso y pulsa Fork → Create fork.

2

En Databricks: perfil → Settings → Linked accounts → Add Git credential.

3

Elige GitHub → Link Git account y autoriza la aplicación.

4

Selecciona Only select repositories y elige tu fork.

5

Crea el Git folder usando la URL de tu fork; desde ahí podrás hacer commit y push.

Si acabas de crear el fork y no aparece, vuelve a abrir la instalación de la Databricks GitHub App y revisa la cuenta seleccionada.

Fuente: Databricks · Connect your Git provider
